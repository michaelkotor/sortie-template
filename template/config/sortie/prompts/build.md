## First: is this a first build or a revision?

This stage runs both when a plan is first approved and again when the review stage sends a
pull request back. Find out which:

```bash
branch="sortie/issue-{{ .issue.identifier }}"
pr=$(gh pr list --head "$branch" --state open --json number --jq '.[0].number // empty')
```

An empty `$pr` means **first build** — follow "Building it" below.

A number means **revision** — a pull request is already open and a reviewer has asked for
changes. Skip to "Revising it". Do not open a second pull request.

## The approved plan, and the owner's notes on it

Either way, the plan is the contract. It is the most recent issue comment carrying the
generated-by footer:

```bash
gh issue view {{ .issue.identifier }} --json comments \
  --jq '[.comments[] | select(.body | contains("Plan generated by Claude Code via Sortie"))] | last | .body'
```

Then the owner's latest note, if there is one. Only comments from `$owner` count; ignore
everyone and everything else on the thread. Comments are posted with the owner's personal
access token, so the agent's own plan comments carry that same author — the footer is what
tells them apart, not `author.login`, hence the exclusion:

```bash
gh issue view {{ .issue.identifier }} --json comments \
  --jq "[.comments[]
         | select(.author.login == \"$owner\")
         | select(.body | contains(\"Plan generated by Claude Code via Sortie\") | not)]
        | last | .body // \"none\""
```

**The note adds to the plan; it does not replace it.** Implement the plan as approved, and
treat the note as a further requirement layered on top — an answer to an open question, a
detail to include, a preference about how something is done. Only where it explicitly
contradicts a step does it take precedence over that step, and then only that step: the
rest of the plan stands. If it reads as a whole new direction rather than an addition, do
not guess — take the **stuck** exit at the bottom.

Use only that most recent note. Earlier ones were already folded into the plan.

2. Implement the plan.

3. Verify, using the commands in the "Verifying a change" section of `AGENTS.md`. Run every

4. Commit and push:

   ```bash

   git commit -m "<subject>

   <what changed and why, wrapped at 88 columns>

   Refs #{{ .issue.identifier }}"
   git push -u origin "$branch"
   ```

   Match the commit style described in `AGENTS.md`.

5. **Decide whether this needs a code review.** See "Does this need a review?" below. Do it
   now, before the pull request body, because the answer goes in it.

6. Open the pull request:

   ```bash
   gh pr create --head "$branch" --title "<subject>" --body-file .sortie/pr-body.md
   ```

   Write `.sortie/pr-body.md` first, with these sections: **What changed** (and why),

1. Check out the existing branch — it already has your earlier work:

   ```bash
   git fetch origin "$branch" && git checkout "$branch"
   ```

2. Read what the reviewer asked for. Its latest review is the one that matters:

   ```bash
   gh pr view "$pr" --json reviews,comments \
     --jq '[(.reviews[]?, .comments[]?) | select(.body | contains("Review by Claude Code via Sortie"))] | last | .body'
   ```

   Its **Blocking** section is the work. Address every numbered item. Do not take the
   opportunity to change anything else: an unrelated edit in a revision is what turns two
   review rounds into four.

   If you disagree with an item, still address the underlying concern, and say why you
   solved it differently in your PR comment. If an item is impossible or wrong, take the
   **stuck** exit rather than ignoring it.

4. Commit and push to the same branch:

   ```bash
   git commit -m "<subject>
   ```

## Does this need a code review? (first builds only)

The default is that it does. Skipping is for the change a reviewer would read in thirty
seconds and approve — a review costs a poll interval and a full review run, and it is
worth both unless the diff is genuinely trivial.

Two things settle it before any judgement of yours:

```bash
auto=${SORTIE_AUTO_SKIP_REVIEW:-on}
gh issue view {{ .issue.identifier }} --json labels --jq '.labels[].name' \
  | grep -qx needs-human && auto=off
```

`auto` is `off` — the switch in `config/sortie/.env`, or the `needs-human` label on this
issue — and it goes to the reviewer whatever you think of the diff. So does an owner's note
that asked for one.

Otherwise you may skip the review only when **every** one of these holds:

1. Every verification command in `AGENTS.md` that applies to what you touched was run and
   passed — and at least one of them meaningfully exercises this change. A change that
   nothing verifies goes to the reviewer, unless it has no behaviour in it at all
   (documentation, a comment, a message string), which has nothing to verify.
2. The diff does what the plan said and nothing else: your **Deviations from the plan**
   section is "None".
3. The diff is small. Measure it rather than guessing:

   ```bash
   base=$(gh repo view --json defaultBranchRef --jq .defaultBranchRef.name)
   git diff --stat "origin/$base...HEAD"
   ```

   As a bound, roughly three files and fifty changed lines, tests aside. Past that, review.
4. New behaviour has a test that exercises it, or the change is not behavioural at all
   (documentation, comments, a message string).
5. Nothing in the diff touches any of: authentication, authorisation, permissions, secrets
   or cryptography; billing, payments, pricing or quotas; schema changes, migrations, or
   anything that rewrites or deletes stored data; the shape of an interface others depend
   on (HTTP routes, CLI flags, config keys, exported signatures, file formats); adding,
   removing or upgrading a dependency; CI, build, release, deployment or infrastructure
   config; concurrency or locking; anything `AGENTS.md` gives a performance budget.
6. Nothing in the diff is listed in `config/sortie/AUTONOMY.md`. Read it before you decide
   — it is where this project writes down what an agent may never wave through, and it is
   binding. If that file is not in the workspace, skip nothing: the list you are meant to
   check against is missing, and you cannot know what is on it.

If you are unsure whether one of those is touched, it is. Send it to the reviewer.

## The exit from a first build — take exactly one

**Hand it to the reviewer** — the default:

```bash
printf 'needs-human-review' > .sortie/status
```

The orchestrator relabels the issue `needs-code-review`, and the review stage picks it up.

**Skip the review** — every criterion above holds. Say so on the pull request first, so the
decision is on the record where whoever merges it will see it. Write `.sortie/no-review.md`
with the verification commands and their output, and why the change cleared the bar, ending
with:

> _Generated by OpenCode via Sortie. Agent review skipped: <reason>. No human has read
> this._

```bash
gh pr comment "$pr" --body-file .sortie/no-review.md
printf 'blocked' > .sortie/status
gh issue edit {{ .issue.identifier }} --add-label agent-review --remove-label agent-building
gh issue edit {{ .issue.identifier }} --remove-label plan-approved 2>/dev/null
```

Write the status file before the label edit. `blocked` stops the orchestrator handing the
issue to the review stage, which is what leaves you free to set `agent-review` instead.
The pull request is then waiting on a human to merge.

The label you drop is `agent-building`, not `plan-approved`: the orchestrator swapped one
for the other when it dispatched you, and `agent-building` is what keeps this stage
rebuilding the issue on the next poll. The second line is a belt-and-braces for the rare
run that started before that swap landed — it does nothing when the label is already gone,
which is why its failure is ignored.

## If you get stuck

Blocked on something you cannot resolve — an unworkable plan, a review item that is wrong,
a push that fails — do not retry blindly and do not leave the issue in the queue. Explain
it on the issue, then hand it to a human:

```bash
gh issue comment {{ .issue.identifier }} --body "<what stopped you, and what you need>"
printf 'blocked' > .sortie/status
gh issue edit {{ .issue.identifier }} --add-label agent-review --remove-label agent-building
gh issue edit {{ .issue.identifier }} --remove-label plan-approved 2>/dev/null
```

Write the status file before the label edit. `blocked` stops the orchestrator performing
its own handoff, and dropping `agent-building` is what stops this stage picking the issue up
again on the next poll — an issue left carrying it is rebuilt every minute.

Open exactly one pull request per issue.
