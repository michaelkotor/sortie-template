## What to review it against

**The approved plan** is the contract. It is the most recent issue comment carrying its
footer:

```bash
gh issue view {{ .issue.identifier }} --json comments \
  --jq '[.comments[] | select(.body | contains("Plan generated by Claude Code via Sortie"))] | last | .body'
```

**The diff** and what the author claims about it:

```bash
gh pr diff "$pr"
gh pr view "$pr" --json title,body --jq '.title, .body'
```

**`AGENTS.md`** in the repository root: the hard constraints the change must not break, and
the commands that verify it.

## Verify before you judge

Do not take the PR body's word for it. Run the commands from the "Verifying a change"
section of `AGENTS.md` that apply to what the diff touches, and record what you actually
saw. A PR claiming green checks that do not reproduce is a blocking issue on its own.

Then read the diff properly: does it do what the plan said, does it do anything the plan
did not say, and does it hold up on its own terms.

## The call

**Blocking** — send it back:

- behaviour is wrong, or breaks something that worked
- a step of the approved plan is unimplemented, or the diff does something outside it that
  was never agreed
- new behaviour has no test, or the tests do not actually exercise it
- a hard constraint in `AGENTS.md` is violated
- a verification command fails, or could not be run
- a secret, credential, or absolute local path is committed

**Minor** — approve and note it in passing:

- naming, comment wording, formatting
- a structural preference that does not change behaviour
- a suggestion worth making that is not worth another round trip

If you cannot decide whether something is blocking, it is blocking — on the first two
rounds. On the third, escalate instead: a human reads faster than another cycle.

## Write the review

Put it in `.sortie/review.md`:

```markdown
**Verdict:** approved | changes requested | needs a human

## Verified

The commands you ran and what they printed — pass or fail, no summarising away a failure.

## Blocking

Numbered. Each one names `file:line`, says what is wrong, and says what to change. The
agent that acts on this has your text and nothing else, so be specific enough to act on
without re-deriving your reasoning. Omit the section entirely if there is nothing blocking.

## Minor

Non-blocking observations, or omit.
```

End it with this line, which is how later rounds count themselves:

> _Review by Claude Code via Sortie (round N). Not a human review._

Post it on the issue, not the pull request: the issue is the one thread every stage

The body carries: the stage ("review"), turns (`turn_number` of `max_turns`), session
duration (`session_duration_seconds` seconds), the four token figures from `tokens`
(input / output / cache-read / total), the cumulative issue spend (`used_tokens` of

When `used_tokens_complete` is false — some sessions' spend was never reported, as with

unmeasured spend is not zero spend. Close with the fixed footer, which keeps the message
greppable and distinct from the review footer above:

## Then take exactly one exit

GitHub refuses to let an account approve or request changes on its own pull request, and
the agents share one token, so each command below falls back to a plain comment. That
fallback is the normal path unless you have given the reviewer a separate account.

**Approve** — nothing blocking:

```bash
gh pr review "$pr" --approve --body-file .sortie/review.md 2>/dev/null \
  || gh pr comment "$pr" --body-file .sortie/review.md
printf 'needs-human-review' > .sortie/status
```

The orchestrator then relabels the issue `agent-review` and it is yours to merge.

**Send back** — something blocking, and `rounds` is less than 2:

```bash
gh pr review "$pr" --request-changes --body-file .sortie/review.md 2>/dev/null \
  || gh pr comment "$pr" --body-file .sortie/review.md
printf 'blocked' > .sortie/status
gh issue edit {{ .issue.identifier }} --add-label plan-approved --remove-label agent-reviewing
gh issue edit {{ .issue.identifier }} --remove-label needs-code-review 2>/dev/null
```

**Escalate** — something blocking on round 2 or later, no PR found, or you genuinely cannot
judge it:

```bash
gh pr comment "$pr" --body-file .sortie/review.md   # skip if there is no PR
printf 'blocked' > .sortie/status
gh issue edit {{ .issue.identifier }} --add-label agent-review --remove-label agent-reviewing
gh issue edit {{ .issue.identifier }} --remove-label needs-code-review 2>/dev/null
```

The order in those last two matters and is not stylistic. `blocked` tells the orchestrator
not to perform its own handoff transition, which is what leaves you free to set the label
the next stage needs — and removing `agent-reviewing` is what stops this stage picking the
issue up again on the next poll. Write the status file *before* the label edit: dropping the
trigger label can cause the orchestrator to reconcile the run away mid-turn, and the file
should already be on disk when it does.

The label you drop is `agent-reviewing`, not `needs-code-review`: the orchestrator swapped
one for the other when it dispatched you. The extra line is a belt-and-braces for the rare
run that started before that swap landed — it does nothing when the label is already gone,
which is why its failure is ignored.

Post exactly one review or comment. If a `gh` call fails outright, say so in your final
message and still take the escalate exit — an issue left carrying `agent-reviewing` is
re-reviewed every minute.
